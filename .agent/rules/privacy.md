# Privacy

This file controls how private records are read and how member data is held. It
does not control who a member is. That is rules/auth.md.

## What counts as private

A private record belongs to one member. This list is authoritative for the CI
check in rules/ci.md check 3.

Member, MemberSession, CheckIn, CheckInCode, LedgerEntry, Payment,
PaymentAttempt, MembershipChange, QuestionLog, PrivateAccessLog.

Version three removed ActivationCode from this list, because the model no longer
exists. It added CheckInCode, because a code is now bound to one member.

Any model marked private in a schema comment must appear here. Adding one means
editing this list and the CI check in the same change.

## The five access rules

1. A private record is read by exact member ID taken from the server session.
2. A member ID in a request body, query string or header is ignored.
3. A private record is never searched across members and never embedded.
4. Every private read writes an access log row.
5. No private field value ever reaches a log line, an error message, an
   exception message, or any analytics or monitoring payload. Log the member ID
   and the function name if you must log anything.

Reason for rule 2: the whole protection collapses if any path lets a caller name
the member they want.
Reason for rule 5: logs are copied into support threads and screenshots, and a
crash reporter will happily upload a stack trace containing a balance.

## The one lookup that is not by member ID

The verifier looks a check in code up by its digits, not by member ID. See
rules/checkin.md.

This is the single exception and it is narrow. The lookup returns at most one
active row, it returns only that row's own member ID, and it exists in one
function in one file. It never returns any other private field, and its result
is never shown to anyone.

Reason: a keypad knows digits and nothing else. There is no way to make that
lookup member scoped. Making the exception explicit here is what stops it
spreading.

## How reads are shaped

- Every exported function under src/server/private/ takes the member ID as its
  first argument.
- That ID reaches the argument from src/server/auth/session.ts and nowhere else.
- The access log row records the session member ID, the target member ID and the
  calling function name. It is written inside the same function as the read.

Reason: a log the caller is responsible for writing is a log that gets skipped.

## The detector

A scheduled job asserts that no access log row exists where the session member
ID differs from the target member ID. Any such row is surfaced to the owner and
to the developer. See rules/jobs.md.

This is now the primary detector, not a backstop. Version three removed the one
device rule, so nothing else would catch a cross member read.

## Passwords and emails

A password hash is never read outside the login and password change paths in
src/server/auth/. It is never returned by any private read function, never
included in any owner screen response, and never embedded.

An email address is a private field. It appears on owner screens, because the
owner needs it to identify a member, and nowhere else.

## Model calls and private data

rules/ai.md owns the rule that the model never receives a private record and
never produces a private figure. Do not restate it in code comments here.

## The privacy notice

Shown during sign up and accepted before the account row is created. One screen,
same plain English as the rest of the app. It states:

- What is stored and who sees it, including her email address and her check in
  history.
- How long each kind of data is kept.
- How to ask for a copy or a deletion.
- That the owner can see her question text with her member number attached,
  because he cannot correct a wrong record without knowing whose it is.
- That check in codes are generated by her, and that a check in records a
  claimed arrival.

The last line matters. She should not believe the gym has proof of where she was
when it does not.

## Controller and processor

The gym is the data controller. The developer is a processor acting on the gym's
instructions. Stated in the notice and in the contract.

Reason: under the Nigeria Data Protection Act the distinction decides who
answers for a breach.

## Retention

- Attendance, question logs, access logs and check in codes: twenty four months.
- Payment records and receipts: seven years, because they are financial records.
- Member identity records, including email and password hash: while active, and
  twenty four months after cancellation.

Deletion is computed from timestamps the models already carry. No retention
field is needed and none should be added. The deletion operation itself is not
in version one.

## Exit

If the gym ends the contract, the owner receives a full export of all gym and
member data within fourteen days. All data is deleted from the developer's
systems within thirty days of the export being confirmed.

## OPEN

The export format and the deletion mechanism are not specified. Ask before
building either.
