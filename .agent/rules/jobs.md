# Jobs

This file controls scheduled work. There is one job. Not two, and not three.

## Why one

Version two had two jobs. One generated a daily check in code for the whole gym.
Version three deleted it, because codes are now generated by members on demand.

A second job would be needed only to maintain membership status, and status is
computed rather than stored precisely so that job does not exist. See
rules/membership.md.

If you find yourself needing another job, stop and ask. It usually means
something is being stored that should be derived, or something is being done on
a schedule that should happen when a member acts.

## The endpoint and the secret

The job is a route handler under src/app/api/jobs/, with the logic in
src/server/jobs/.

The endpoint requires the shared secret in a request header. It never accepts it
in a query string, and it rejects anything without it.

Reason: a query string lands in server logs, browser history and referrer
headers. A public URL that mutates data is an open door.

## Which clock

The scheduler runs in UTC. The time below is local to the gym.

Convert once, in the schedule configuration, using the gym's fixed offset.
Nigeria does not observe daylight saving, so the offset is constant. Do not
write a job that reads a local time and assumes the server agrees.

## The nightly sweep

Runs at three in the morning, gym local time. Four tasks in one run.

1. Marks any payment attempt still pending after twenty four hours as abandoned
   and surfaces it to the owner. It never marks one failed, because the money
   may have moved.
2. Deletes check in codes that expired without being consumed and are older than
   the retention window.
3. Asserts that no private access log row exists where the session member ID
   differs from the target member ID. Surfaces any such row to the owner and to
   the developer.
4. Computes the counts on the owner's weekly review page.

Task 2 is housekeeping only. An expired code is already unusable, because the
verifier checks the timestamp on every attempt. The job removes the rows so the
table does not grow. Never let expiry depend on this job running.

Reason: a job that is load bearing for correctness fails silently the first
night it does not run.

## Rules for the job

- It is idempotent. Running it twice in one night changes nothing the second
  time.
  Reason: schedulers retry.
- It never sends anything to a member. No message, no reminder, no nudge, in any
  channel.
  Reason: version one never initiates contact, and a scheduled job is the
  obvious place that rule would break.
- It logs a start line and a finish line with a count of what it touched.
  Reason: a silent job that stopped running looks exactly like a job with
  nothing to do.
- A failure is visible. It does not swallow its error.
- One task failing does not stop the others. Each task catches its own error,
  records it, and the job continues.
  Reason: an abandoned payment sweep must not be skipped because a count query
  broke.

## Not jobs

Check in code expiry is not enforced by a job. The verifier checks the
timestamp. See rules/checkin.md.

Retention deletion for member data is a later operation, not in this job. See
rules/privacy.md.

Reindexing is not a job. It happens when the owner approves a card. See
rules/retrieval.md.

Session expiry is not a job. A session is checked on use. See rules/auth.md.
